# 服务机器人中间件与基础设施软件设计方案

## 1. 项目概述

### 1.1 项目背景

随着服务机器人在家庭、商业、医疗等场景的广泛应用，传统的单体式机器人软件架构已难以满足复杂任务需求。本项目旨在构建一套面向服务机器人的通用中间件与基础设施平台，以ROS 2为基础，融合VLA（Vision-Language-Action）与世界模型作为决策核心，提供数据采集、回放、仿真等全链路能力支撑。

### 1.2 设计目标

- **高性能**：域内共享内存通信，微秒级延迟，满足实时控制需求
- **可扩展**：模块化、插件化架构，支持功能模块动态加载
- **多模态**：支持视觉、语言、力觉、激光等多传感器融合
- **闭环迭代**：采集-训练-仿真-部署的完整数据飞轮
- **确定性**：实时操作系统级别的任务调度与通信保障

### 1.3 适用场景

- 家庭服务机器人（清洁、陪伴、看护）
- 商业服务机器人（酒店、餐厅、零售）
- 医疗辅助机器人
- 工业协作机器人

### 2.2 架构原则

1. **关注点分离**：每一层只关注自身职责，通过标准接口交互
2. **接口优先**：依赖抽象而非具体实现，支持模块替换
3. **容错设计**：关键模块冗余，故障降级不崩溃
4. **数据驱动**：以数据流为核心，松耦合组件协作

## 3. 中间件层设计

### 3.1 ROS 2 基础架构

本方案基于 ROS 2 Humble / Jazzy 长期支持版本，利用其成熟的节点管理、服务发现、参数系统等基础设施。

#### 3.1.1 核心组件

| 组件 | 功能说明 | 技术选型 |
|------|---------|----------|
| 节点管理 | 节点生命周期管理、动态加载 | rclcpp_lifecycle + pluginlib |
| 参数服务 | 配置参数的集中管理与动态更新 | rclcpp parameters + parameter server |
| 服务发现 | 自动发现节点、话题、服务 | DDS Discovery + ros2cli |
| 时间同步 | 多传感器时间戳对齐 | message_filters + NTP/PTP |
| 日志系统 | 分级日志、远程收集 | rclcpp logging + Fluentd |

#### 3.1.2 自定义扩展

在 ROS 2 基础上，扩展以下中间件能力：

- **节点编排引擎**：基于 YAML 的节点拓扑声明式配置，支持启动/停止/重启策略
- **健康检查框架**：节点心跳、资源监控、故障自愈
- **配置中心**：多环境配置管理、版本化、灰度发布
- **权限控制**：节点间通信的 ACL 访问控制

### 3.2 通信抽象层 (DAL - Data Access Layer)

为屏蔽底层通信协议差异，设计统一的通信抽象层，对上层提供一致的发布/订阅、请求/响应接口。

```cpp
// 通信抽象层核心接口概念
class IPubSubTransport {
public:
    virtual bool createPublisher(const std::string& topic, const std::string& type) = 0;
    virtual bool createSubscriber(const std::string& topic, const std::string& type,
                                   DataCallback callback) = 0;
    virtual bool publish(const std::string& topic, const void* data, size_t size) = 0;
    virtual ~IPubSubTransport() = default;
};
```

#### 3.2.1 域内通信 - 共享内存

**设计目标**：单机器人内部模块间通信，追求极致低延迟（< 100μs）和高吞吐量。

**技术方案**：

- **实现基础**：基于 POSIX 共享内存（shm_open + mmap）+ 无锁环形缓冲区（Lock-Free Ring Buffer）
- **序列化**：零拷贝传递，仅传递指针和大小，复杂类型使用 FlatBuffers / Cap'n Proto
- **同步机制**：原子操作 + 信号量（sem_t），避免系统调用开销
- **内存池**：预分配共享内存池，减少动态分配延迟

**共享内存通道架构**：

```
┌─────────────────── 共享内存区域 ───────────────────┐
│                                                     │
│  ┌─────────────── Control Block ────────────────┐  │
│  │  magic | version | ring_count | writer_mask  │  │
│  │  reader_mask | sequence | timestamp | ...    │  │
│  └───────────────────────────────────────────────┘  │
│                                                     │
│  ┌─────────────── Ring Buffer 0 ────────────────┐  │
│  │  slot[0] | slot[1] | ... | slot[N-1]         │  │
│  │  (每个slot含: header + payload)              │  │
│  └───────────────────────────────────────────────┘  │
│                                                     │
│  ┌─────────────── Ring Buffer 1 ────────────────┐  │
│  │  (多通道隔离，不同优先级)                     │  │
│  └───────────────────────────────────────────────┘  │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**关键特性**：

- **多优先级队列**：实时控制指令（如电机控制）走高优先级通道，传感器数据走普通通道
- **多读者单写者**：支持一对多广播，读者独立维护读指针
- **背压机制**：缓冲区满时的策略可配置（丢弃旧数据 / 阻塞写入 / 动态扩容）
- **心跳与健康检测**：定期更新时间戳，异常进程自动清理

#### 3.2.2 域间通信 - DDS

**适用场景**：多机器人协作、机器人与边缘计算节点间通信。

**技术方案**：

- **DDS 实现**：默认使用 Fast DDS（ROS 2 默认），支持切换 Cyclone DDS
- **QoS 配置**：
  - 实时控制：RELIABLE + VOLATILE + KEEP_LAST(1)
  - 传感器数据：BEST_EFFORT + VOLATILE + KEEP_LAST(1)
  - 状态数据：RELIABLE + TRANSIENT_LOCAL + KEEP_LAST(1)
- **发现机制**：支持组播发现和静态发现（确定性场景）
- **安全插件**：DDS Security（认证、加密、访问控制）

#### 3.2.3 云边通信 - MQTT / WebSocket

**适用场景**：机器人与云端服务、移动端 App、Web 控制台通信。

**技术方案**：

- **MQTT Broker**：EMQX / Mosquitto，支持 QoS 0/1/2
- **协议桥接**：ROS 2 ↔ MQTT 双向桥接节点，支持话题映射
- **WebSocket**：Web 端实时数据推送，基于 rosbridge 协议
- **消息压缩**：大体积传感器数据使用 zstd / lz4 压缩
- **断连缓存**：网络中断时本地缓存，恢复后自动续传

### 3.3 节点生命周期管理与启动编排

系统中存在数十个节点，启动顺序、依赖关系、状态同步直接影响系统可靠性。设计统一的节点生命周期管理框架。

#### 3.3.1 节点生命周期状态机

每个节点遵循统一的生命周期状态机：

```
            ┌──────────┐
            │  UNCONFIGURED  │  (初始状态，资源未分配)
            └──────┬───────┘
                   │ configure()
                   ▼
            ┌──────────┐
            │ INACTIVE │  (已配置，未激活)
            └──────┬───────┘
                   │ activate()
                   ▼
            ┌──────────┐
     ┌─────▶│  ACTIVE  │──────┐  (正常运行)
     │      └──────┬───────┘      │
     │ error       │ deactivate   │ error
     ▼             ▼              ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│ ERROR    │ │ INACTIVE │ │ FINALIZED│
│ (故障)   │ │          │ │ (终止)   │
└──────────┘ └──────────┘ └──────────┘
     │
     └── 故障恢复/重启 ──┘
```

**状态说明**：

| 状态 | 说明 |
|------|------|
| UNCONFIGURED | 节点对象已创建，但未加载配置、未申请资源 |
| INACTIVE | 配置已加载，资源已分配，订阅/发布已注册，但不处理数据 |
| ACTIVE | 正常运行，处理数据并发布结果 |
| ERROR | 发生故障，自动停止处理，等待恢复 |
| FINALIZED | 优雅退出，资源已释放 |

#### 3.3.2 启动依赖与拓扑排序

每个节点声明自己的依赖（哪些节点必须先就绪），Launcher 根据依赖关系进行拓扑排序，保证启动顺序正确。

```yaml
# 启动编排配置示例 (launch.yaml)
nodes:
  - name: hal_camera
    type: hal::CameraNode
    depends_on: []         # 无依赖，最先启动
    params:
      fps: 30

  - name: gdc_process
    type: perception::GdcProcessNode
    depends_on: [hal_camera]  # 依赖相机节点就绪
    params:
      model_path: /models/yolov8.engine

  - name: fake_vla
    type: decision::FakeVlaNode
    depends_on: [gdc_process]  # 依赖感知节点就绪
    params:
      instruction: "go to the cup"
```

**启动流程**：

1. Launcher 解析配置，构建依赖图
2. 拓扑排序，确定启动顺序
3. 按顺序调用 `configure()` → `activate()`
4. 等待节点发布 **Ready 信号** 后，再启动下一批
5. 所有节点就绪后，系统进入正常运行状态

#### 3.3.3 就绪屏障（Ready Barrier）

**问题**：先启动的节点发布消息时，后启动的订阅者还没注册，导致首帧数据丢失。

**解决方案——就绪屏障**：

1. 所有节点先完成 `configure()`（注册发布者和订阅者）
2. 所有节点处于 INACTIVE 状态，**不发布任何数据**
3. Launcher 确认所有节点的发布/订阅都已注册完毕（DDS 发现完成）
4. Launcher 广播 **"/system/activate"** 信号
5. 所有节点收到信号后同时进入 ACTIVE 状态，开始发布数据

```
时间轴:
  t0: 节点A configure() → 注册 pub/sub
  t1: 节点B configure() → 注册 pub/sub
  t2: 节点C configure() → 注册 pub/sub
      ... (等待 DDS 发现完成) ...
  t3: Launcher 广播 ACTIVATE 信号
  t4: 所有节点同时开始收发数据 ✅ 无首帧丢失
```

#### 3.3.5 共享内存模式下的注册保障

对于共享内存通信（非 DDS 自动发现），需要更显式的注册机制：

- **共享内存管理节点 (SHM Manager)**：集中管理所有共享内存通道的创建
- 节点启动时向 SHM Manager 注册（声明要发布/订阅的 topic）
- SHM Manager 创建/映射共享内存区域后，通知节点就绪
- 所有节点注册完成后，Launcher 才触发激活

```
节点A                    SHM Manager                   节点B
  │                          │                            │
  ├─ register_pub(topic1) ──▶│                            │
  │                          │ create shm channel         │
  │                          │◀─ register_sub(topic1) ────┤
  │                          │                            │
  │  ◀──── map_channel() ────┤──── map_channel() ───────▶│
  │                          │                            │
  │  ◀─── activate all ──────┤──── activate all ────────▶│
  │                          │                            │
```

### 3.4 通信域划分

根据实时性和安全等级，将系统划分为多个通信域：

| 域名称 | 范围 | 通信方式 | 典型延迟 | 安全等级 |
|--------|------|---------|---------|---------|
| 实时控制域 | 运动控制、电机驱动 | 共享内存 | < 100μs | 最高 |
| 感知融合域 | 传感器、感知算法 | 共享内存 | < 1ms | 高 |
| 决策规划域 | VLA、世界模型、规划 | 共享内存 + DDS | < 10ms | 中 |
| 人机交互域 | 语音、UI、App | MQTT / WebSocket | < 100ms | 中 |
| 云边协同域 | 云端服务、数据上传 | MQTT / HTTP | 网络依赖 | 低 |

**域间网关**：不同域之间通过专用网关节点进行数据转发，实现流量控制、格式转换、安全隔离。

## 4. 决策层设计（VLA + 世界模型）

### 4.1 VLA 决策引擎

VLA（Vision-Language-Action）是将视觉感知、语言理解与动作执行统一建模的端到端决策框架。

#### 4.1.1 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                     VLA 决策引擎                          │
│                                                           │
│  ┌──────────┐    ┌──────────────┐    ┌───────────────┐  │
│  │ 视觉编码器│───▶│  多模态融合  │───▶│  动作解码器    │  │
│  │(ViT/CLIP)│    │(Cross-Attn)  │    │(Action Head) │  │
│  └──────────┘    └──────────────┘    └───────────────┘  │
│        ▲                ▲                    │           │
│        │                │                    ▼           │
│  ┌──────────┐    ┌──────────────┐    ┌───────────────┐  │
│  │ 语言编码器│    │  历史状态    │    │  动作执行器    │  │
│  │(LLaMA/   │    │  缓存        │    │  (低阶策略)   │  │
│  │ BERT)    │    │              │    │               │  │
│  └──────────┘    └──────────────┘    └───────────────┘  │
│                                                           │
└─────────────────────────────────────────────────────────┘
```

#### 4.1.2 关键模块

**视觉编码器**：
- 输入：多摄像头图像（RGB + 深度）、点云
- 骨干网络：ViT-L / CLIP-ViT / DINOv2
- 特征输出：多尺度视觉特征序列

**语言编码器**：
- 输入：自然语言指令、对话历史
- 模型：LLaMA-2 / Qwen / Mistral（按需裁剪）
- 特征输出：语言嵌入向量序列

**多模态融合**：
- 采用 Cross-Attention 机制
- 支持指令引导的视觉特征选择
- 历史状态注入（Transformer 记忆）

**动作解码器**：
- 离散动作：词汇表式动作 token（如 RT-2）
- 连续动作：直接回归关节角度 / 末端位姿
- 混合动作：高层语义动作 + 低层连续控制

#### 4.1.3 推理部署

- **模型量化**：INT8 / FP16 量化，TensorRT / ONNX Runtime
- **推理加速**：NVIDIA Jetson / 昇腾 / 瑞芯微 NPU 适配
- **流式推理**：增量解码，降低首帧延迟
- **模型热切换**：支持不同场景模型的动态加载

### 4.2 世界模型引擎

世界模型用于对环境状态进行编码、预测和仿真，为决策提供"想象"能力。

#### 4.2.1 世界模型架构

```
┌─────────────────────────────────────────────────────────────┐
```

#### 5.1.2 采集数据类型

| 数据类别 | 具体内容 | 典型频率 | 数据格式 |
|---------|---------|---------|---------|
| 视觉数据 | RGB图像、深度图、点云 | 30-60Hz | ROS Image / PointCloud2 |
| 音频数据 | 麦克风阵列、语音 | 16kHz | PCM / WAV |

#### 5.1.3 关键特性

**精确时间同步**：
- 基于 PTP (Precision Time Protocol) 的硬件级时间同步
- 软件层多传感器时间戳插值对齐
- 支持硬件触发（硬同步）和软件触发（软同步）

**数据完整性保障**：
- 环形缓冲区防止数据丢失
- 写时拷贝（Copy-on-Write）减少内存占用
- 校验和 / 哈希验证数据完整性

**存储格式**：
- 实时录制：MCAP 格式（推荐，支持随机访问、多线程写入、零拷贝读取）
- 兼容格式：ROS 2 Bag（db3 / sqlite3）
- 消息编码：Protocol Buffers / FlatBuffers（高性能序列化）
- 元数据：自动记录软硬件版本、配置参数、环境信息

**MCAP vs ROS 2 Bag vs Protocol Buffers 选型说明**：

| 维度 | MCAP | ROS 2 Bag (db3) | Protocol Buffers |
|------|------|-----------------|------------------|
| 定位 | 录制/回放文件格式 | 录制/回放文件格式 | 消息序列化库 |
| 随机访问 | 多索引，O(1) 跳转 | 需遍历 SQLite | 不涉及 |
| 写入性能 | 多线程、高吞吐 | SQLite 写入瓶颈 | 不涉及 |
| 回放性能 | mmap 零拷贝 | 数据库查询 | 不涉及 |
| ROS 生态兼容 | 有 rosbag2 存储插件 | 原生支持 | 需自己桥接 |
| 多格式混存 | 支持多种序列化 | 默认仅 ROS 消息 | 自身就是一种格式 |
| 工具链 | Foxglove Studio 强 | ros2 bag 命令行 | protoc 生态完善 |
| 文件体积 | 可压缩，紧凑 | SQLite 有开销 | 不涉及 |

**选型建议**：
- 采用 MCAP 作为录制文件格式（兼顾性能和 ROS 生态兼容性）
- 消息体使用 Protocol Buffers 编码（跨语言、前向兼容、体积小）
- ROS 2 集成方式：`ros2 bag record --storage mcap --serialization cdr`

**边端协同**：
- 本地 SSD 高速缓存（环形覆盖）
- 重要事件数据自动上传云端
- 增量上传、断点续传

### 5.4 数据驱动仿真（Logged Data Driven Simulation）

数据驱动仿真是一种**以真实采集数据驱动软件栈运行**的仿真模式，核心思想是：**同一套业务处理代码，在部署和仿真两种模式下无差别运行**。

#### 5.4.1 核心理念

传统仿真（如 Gazebo / Isaac Sim）是**物理驱动**的：通过物理引擎计算世界状态，再渲染传感器数据。

数据驱动仿真是**数据驱动**的：直接将真实世界采集的传感器数据回灌到软件栈中，业务算法感知不到自己运行在仿真里。

```
┌──────────── 真实机器人部署模式 (ARM) ────────────┐
│                                                    │
│  ┌──────────┐    ┌───────────┐    ┌────────────┐  │
│  │ 真实HAL  │───▶│ gdc_      │───▶│ 决策/控制  │  │
│  │ (摄像头) │    │ process   │    │  模块      │  │
│  └──────────┘    └───────────┘    └────────────┘  │
│                                                    │
└────────────────────────────────────────────────────┘

┌──────────── 数据驱动仿真模式 (x86) ───────────────┐
│                                                    │
│  ┌──────────┐    ┌───────────┐    ┌────────────┐  │
│  │ Data     │───▶│ gdc_      │───▶│ 决策/控制  │  │
│  │ Player   │    │ process   │    │  (Fake)    │  │
│  │ (回灌)   │    │ 【相同代码】│    │            │  │
│  └──────────┘    └───────────┘    └────────────┘  │
│                                                    │
└────────────────────────────────────────────────────┘
```

#### 5.4.2 关键价值

| 价值 | 说明 |
|------|------|
| **代码一致性** | 业务算法代码完全相同，不存在"仿真一套、部署一套"的割裂 |
| **调试效率高** | 在 x86 开发机上就能复现线上问题，用 gdb / 打印自由调试 |
| **算法迭代快** | 新算法在历史数据上跑一遍就能评估效果，不需要每次都上车 |
| **回归测试** | 每次代码变更，自动在历史数据集上跑回归，防止性能退化 |
| **数据飞轮** | 采集 → 回放调试 → 算法优化 → 部署 → 再采集，闭环迭代 |

#### 5.4.3 实现架构

```
┌──────────────────────────────────────────────────────────────┐
│                  业务处理层 (Business Logic)                   │
│                                                                │
│  ┌─────────────┐   ┌─────────────┐   ┌──────────────────┐   │
│  │ gdc_process │   │ 更多算法... │   │  决策/规划模块    │   │
│  │ (感知/识别) │   │             │   │                  │   │
│  └──────┬──────┘   └──────┬──────┘   └────────┬─────────┘   │
│         │                 │                    │              │
│         └─────────────────┼────────────────────┘              │
│                           ▼                                   │
│              ┌───────────────────────────┐                    │
│              │  中间件通信抽象层 (DAL)    │                    │
│              │  (话题发布/订阅统一接口)    │                    │
│              └─────────┬─────────────────┘                    │
│                        ▲ │                                    │
│        ┌───────────────┘ └───────────────┐                    │
│        │ 部署模式                         │ 仿真模式            │
└────────┼─────────────────────────────────┼────────────────────┘
         │                                 │
         ▼                                 ▼
┌──────────────────┐           ┌──────────────────┐
│   HAL 层 (真实)  │           │   Data Player    │
│  - 摄像头驱动    │           │   (数据回放器)   │
│  - 电机驱动      │           │  - MCAP/Bag 读取 │
│  - IMU           │           │  - 时间同步回放  │

```

#### 5.4.4 编译与构建

通过编译选项或运行时配置切换数据来源：

```cpp
// 业务代码完全不感知模式
class GdcProcessNode {
public:
    void init() {
        // 订阅相机话题 —— 真实模式下来自 HAL，仿真模式下来自 Data Player
        sub_camera_ = dal_->createSubscriber("/camera/front", "Image",
            [this](const void* data, size_t size) {
                this->onCameraImage(data, size);  // 同一套处理逻辑
            });
    }

    void onCameraImage(const void* data, size_t size) {
        // 感知算法 —— 部署和仿真用完全相同的代码
        detect_objects(data, size);
        // ...
    }
};
```

**两种模式切换方式**：
1. **编译时切换**：通过 CMake 选项编译不同的 main 入口
2. **运行时切换**：通过配置文件决定启动 HAL 还是 Data Player

## 11. 总结

本方案构建了一套以 ROS 2 为基础、共享内存为域内通信核心、VLA + 世界模型为决策大脑的服务机器人中间件平台。通过分层解耦的架构设计，实现了从硬件驱动到应用层的全链路覆盖，并提供数据采集、回放、仿真等完整工具链，支撑服务机器人的快速开发与迭代。

核心优势：

1. **高性能通信**：共享内存微秒级延迟，满足实时控制需求
2. **智能决策**：VLA + 世界模型双系统协同，兼顾快速反应与长程规划
3. **数据飞轮**：采集-训练-仿真-部署闭环，持续提升能力
4. **工程化完备**：监控、部署、安全、运维全链条覆盖
5. **开放扩展**：模块化设计，易于功能扩展和定制化
